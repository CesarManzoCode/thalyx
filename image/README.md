# The machine

`vault/09-Notas-Tecnicas/Construccion-del-ISO.md`:

> **La imagen contiene el kernel de Linux y un programa: `thalyx`.**

That is written to be countable, and this is how you count it:

```sh
make count
```

If it says anything other than `1 program(s) in the image`, the decree is broken
and the number says so before anyone has to argue about it.

## What has run and what has not

| | |
|---|---|
| `make image`, `make count` | **Tested.** It is `thalyx dev image`, Rust with tests |
| `make binary` | **Run.** Statically linked against musl, checked with `readelf` |
| `make kernel` | **Run.** 6.12.101 builds from `thalyx.config` |
| `make store`, `make run` | **Run.** The machine boots, mounts its store, and takes instructions |
| `make esp`, `make run-uefi` | **Run, 2026-08-06.** A UEFI firmware started the medium with no boot loader in front of it |
| `sudo make installed`, `make run-installed` | **Run, 2026-08-07.** A firmware started a disk Thalyx wrote byte by byte, with no medium attached. That is act 1 of the exit criterion |
| `make run-hardware` | **Never run, anywhere.** The drivers a PC needs, driven through emulated controllers: xHCI, NVMe, AHCI, and the medium as a USB disk. It is not act 2 and does not close it — see the note above the target, which is exact about which half of act 2 it reaches |

`make kernel` is also where anyone finds out what is wrong with
`thalyx.config`. `config-check` compares every option asked for against the one
that came out, because `olddefconfig` drops options whose dependencies are
unmet without saying a word — that is how `BPF_LSM` and `DEBUG_INFO_BTF` were
silently missing once, and the only symptom would have been enforcement failing
to attach three steps later.

## Why an initramfs and not an ISO

An ISO needs a bootloader, a partition table, and a filesystem to hold them. An
initramfs needs none of those: the kernel unpacks a cpio archive into a tmpfs
and runs `/init`. QEMU is handed the kernel and the archive and nothing else.

That is not a shortcut around the decree. It is the decree with nothing left
over — there is no third thing anywhere in the path for something to hide in,
which is exactly how an Alpine base got in last time.

## Why the kernel starts from `allnoconfig`

Because the opposite direction cannot be audited. A distribution kernel with
options switched off still contains everything nobody remembered to switch off,
and nobody can say what is in it. Starting from nothing means what is on is what
somebody decided to put there, and `thalyx.config` is that list with a reason
beside each group.

## The store

Persistent state is on a separate virtio disk, so the root filesystem keeps
nothing across a boot. PID 1 mounts the three subvolumes `Core-Nucleo.md`
decrees; it does not create them. A machine that quietly made itself a new store
whenever it could not find one could never tell you it had lost the old one.

## The agent, and the two things it needs on the disk

Since 2026-08-28 the machine can be spoken to in ordinary Spanish, and the
engine that makes that possible is **a module on the store**, not part of the
image. `make -C image count` still says the image is the kernel and one program,
because a module is not in the image — it is on the disk beside it.

Two inputs, both of them yours to provide. Thalyx never downloads weights.

```sh
# 1. Build llama.cpp's llama-completion, static. A few minutes, once.
make -C image engine

# 2. Build the disk with the engine, a GGUF, and the tier already chosen.
make -C image store-stage MODEL=/path/to/Qwen2.5-1.5B-Instruct-Q4_K_M.gguf
sudo make -C image store

make -C image run
```

Then, at the machine's own screen:

```
crea una carpeta llamada pruebas
ls
```

Without `MODEL` the stage says which piece is missing and builds a disk with no
agent — which is a supported machine, not a broken one. Every verb still works;
the machine says it has no model when you talk to it in your own words.

**Changing the model does not mean rebuilding Thalyx.** The GGUF is a file at
`/opt/thalyx/data/engine/models/model.gguf` on the `modules` subvolume. Put a
different one there and tell the agent about it:

```
thalyx agent model use media --weights /opt/thalyx/data/engine/models/model.gguf     --module dev.thalyx.engine
```

`ENGINE_TIER=media make -C image store-stage MODEL=…` chooses the tier at build
time instead. The tiers are in `vault/02-Arquitectura/Gamas-de-Modelo.md`.

**Memory.** `MEMORY` defaults to 6144 MiB for exactly this: the smallest tier is
about 1.1 GB of weights before any context, and the engine's manifest asks for a
4 GiB ceiling. QEMU allocates it lazily, so a machine that never loads a model
pays nothing.

## Building this needs no bpftool

It used to. `lsm/vmlinux.h` was generated by `bpftool btf dump file
/sys/kernel/btf/vmlinux format c`, which made three things requirements of
*building*: bpftool on the build machine, a kernel with
`CONFIG_DEBUG_INFO_BTF`, and permission to read that file. None of them is
needed to run anything.

The header is now written by hand — about nine structs, which is what the two
programs actually touch. Its offsets are wrong and unused: `preserve_access_index`
makes clang emit a CO-RE relocation naming each field, and Thalyx's own loader
patches the running kernel's real offset in.

What is still needed to build: `clang`, `curl`, `tar`, `cpio`, a Rust toolchain
with the musl target, `mkfs.btrfs`, and `qemu-system-x86_64` to run it.
